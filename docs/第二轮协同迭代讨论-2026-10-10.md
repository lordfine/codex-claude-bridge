# 第二轮协同迭代讨论

状态：已完成本轮代码与验收整理，准备0.22.0发布。最终结果及宿主能力边界见[版本验证](版本验证-0.22.0.md)。

## 依据与已核实事实

依据桌面《连接器复盘与迭代建议-2026-10-10.md》及同日脱敏证据包。报告内容为调查证据与建议，不构成对原业务会话派发、恢复或中断的授权。

- 报告统计窗口为北京时间 2026-10-10 05:36:34 至 17:36:34。报告归因出 141 次 Goal 自动续接，其中 71 轮仅调用观察类工具，记录成本约 10.14 美元。该金额属于优化候选，尚未在本次调查独立重算，不代表全部属于浪费或供应商最终账单。
- 本次已实际运行证据包的纯函数回放脚本，针对已安装 0.21.0 复现三项错误：缺少 turnOrigin 的新版通知误判为人工输入；带尾注的队友包装误判为人工输入；普通用户完整引用队友包装被误判为代理通知。
- 回放证明来源分类存在缺陷，但“外部 CLI 来源”本身不足以证明某段包装必为可信队友消息；修复仍需结合生产者与任务登记证据。
- Goal 宿主调度与桥接事件调度是两个调度来源。插件能否让宿主保持目标活动且不创建新模型轮，正在核查，不能将插件新增等待字段等同于宿主支持。

## 本轮设计树

1. 交付优先级：调度能力核查与确定性状态缺陷并行推进，还是将整个版本绑定宿主调度能力。
2. 省用量的验收边界：关键交付、失败与权限事件及时送达；健康无变化时不产生例行模型调用。支持条件需有真实运行证据。
3. 使用方式：保留低、中、高三档与默认中频；确定是否将调度省用量机制用于所有档位。
4. 验证范围：隔离会话先验证协议，再决定原业务会话是否做受控验证。
5. 宿主能力核查结束后再讨论降级路径；不得擅自把活动目标标为完成、阻塞或暂停。

## 已确认决策

- 首批同时处理通知来源、指定请求回执、失败终态，以及宿主调度能力核查；不因宿主能力不明而延迟可以独立交付的修复。
- 三档都不因普通心跳和无变化超时触发模型；档位差异主要体现阶段交付的合并粒度及普通进度通知频率。关键失败、权限和断连不受低频过滤。

以上两项已获用户确认。默认中频保持不变。

## 本轮新增需求与待确认设计

用户提出：Claude 应能主动通过工具回传执行结果；派工文字应减少主控操作背景，改善人类阅读体验。

建议主动回传与本地观察兜底结合。Claude 提交完成、受阻、需决定等结构化回执，桥接校验所属会话与逻辑请求、保存证据并去重，按档位生成待处理事件。进程崩溃或模型漏报由观察器发现。回传入库、送达主控、主控验收是三个不同事实，不应使用同一个“成功”状态。

主动回传不直接授予执行端操控任意 Codex 会话的能力。目标主控从当前委派绑定解析；重复上报复用事件身份，不能反复唤醒。Claude 声称完成后，仍需 Codex 根据版本和证据验收。

已确认提供同一回传协议的 MCP 入口与 CLI 备用入口，两种入口共用绑定、校验与去重逻辑，并保留观察器兜底。现有代码具有交付文档、托管 hooks、事件队列和主控消费确认，可复用；尚无专供执行端调用的结构化主动回传工具。

现有交付文档没有显式会话 ID 与逻辑请求 ID，观察器按当前记录补入归属。新增协议需绑定实际委派请求，避免迟到回执被归到后续请求。相同回执重试不得重复通知；修订交付需形成明确的新版本，不能只重复阶段编号。

派工正文建议按需包含：任务、范围、验收、交付。首次交接补充必要背景；后续修复只描述差异、证据与本轮预期。请求 ID、去重标记、调度策略等尽量保留在工具字段与本地记录。命令参数、错误原文、业务约束、版本与验收要求不得为追求简短而删除。

示例：

> **任务：修复排队请求的确认回执**
> **范围：** A 正在执行、B 排队时，查询 B 只能返回 B 的状态。
> **验收：** 覆盖 B 未发送、B 已开始和请求不存在三种情况，回执不能串号。
> **交付：** 提交改动版本、检查结果和遗留问题，并调用回传工具。

## 宿主能力核查

本机 Codex CLI 0.160.1 帮助公开提供 queue 与 app-server proxy，可作为向现有宿主投递事件的候选。尚未验证它们与桌面宿主的绑定、去重和写入权语义，不能认定已解决双写入器问题。已查帮助没有证实 active Goal 可进入不产生模型轮的外部等待状态。后续用隔离会话验证，按结果讨论兼容方案。

已确认：若无法验证宿主静默等待能力，新建的长时间委派默认采用桥接事件驱动，不同时启用 Goal 自动续接。已有活动 Goal 仅明确提示冲突与切换方式，不擅自更改其状态。保留目标及进度不等于必须让 Goal 宿主持续调度；这两种运行方式的兼容边界须在界面和技能中明确说明。

## 实施顺序与交付范围

1. 修复可复现的来源分类、指定请求回执和失败终态问题；用证据包正反例验证，避免通过放宽文本匹配冒认系统来源。
2. 复用现有事件队列，增加执行端 MCP 主动回传、CLI 备用入口与可查询收据；绑定会话和逻辑请求，区分保存、主控领取、业务验收。保留本地观察兜底。
3. 精简派工模板与协作技能；按任务、范围、验收、交付组织正文，首次交接才补充必要背景。
4. 隔离验证宿主事件投递与唯一写入器；无法证明 Goal 静默等待时采用已确认的事件驱动默认方案。三档均不因普通心跳或无变化超时唤醒模型。
5. 继续按证据逐项处理权限菜单分类、后台生命周期、当前轮证据补充、重试收敛、游标作用域、交付版本、诊断脱敏与用量归因。可以分批交付，不将未完成项目标为已修复。

先使用新建隔离会话完成回传、故障和调度实测。验收包含真实 Claude 回传与 Codex 处理、重复回传去重、漏报兜底，以及健康等待期间主控模型调用计数。原业务会话恢复由用户另行发起。

## 验证安排

- 先使用隔离的新会话完成实测；原业务恢复保留为用户另行发起的动作。
- 用户追加资源收尾要求：确认无复用价值后，清理连接器自建会话、专用分支和工作区；保留原项目及仍有成果的资源，记录实际清理结果。详见[主动回传与收尾](主动回传与收尾.md)。

## 验证约束

保留报告中的 20 个回归场景作为候选验收矩阵，逐项标明通过、失败、未验证或受宿主能力限制。不能用配置成功代替实际送达，也不能用本地零模型调用替代主控零模型调用。费用比较应保留缓存成本及缺价情况，不预先承诺整体降幅。
