# 最佳实践

目标是让 Codex 把精力花在任务安排和判断上，让 Claude 有足够清楚的执行范围。下面的建议对应本项目已实现的协作方式，功能限制见 [功能与限制](./功能与限制.md)。

## 1. 任务写成一份小型交付说明

最好同时写出工作目录、目标、允许修改的范围与验收条件。可以复制这个模板：

```text
工作区：〈Git 仓库绝对路径〉
目标：〈用户能观察到的结果〉
修改范围：〈允许修改的模块／文件〉
保留约束：〈必须保持的行为、明确不改的部分〉
验收条件：〈可检查的结果，以及希望执行的检查〉
执行方式：普通终端托管；新任务使用独立工作树
模型：继承当前配置
交付：安排独立审查，向我汇报差异和验收结论；先不要合并
遇到业务取舍：先问我
```

例如，把“优化登录”写成“登录失败时显示服务端错误说明，保持鉴权与路由不变，验收密码错误和网络失败两种提示”。Codex 可以据此拆分任务，Claude 也有明确的完成标准。

## 2. 用一个小任务熟悉完整过程

先做 README 修改、单个缺陷修复或范围清楚的小功能。第一轮保留“先不要合并”，观察执行目录、窗口、差异与验收结果。确认模型和流程稳定后，再增加并发或后台续接。

简单的一处修改可以直接让 Codex 做。适合委派的工作通常有清楚边界、需要持续实现，或需要独立审查；不必把所有动作都变成多代理任务。

## 3. 并行按修改范围拆，不只按角色拆

“前端改独立页面，后端改独立接口”比“几个 Claude 一起改同一个公共文件”更容易协调。依赖尚未确定时先让 Codex 定接口，再派发实现。

普通托管默认并发 3 个顶层会话、最多 10，超额排队。首次使用先一个任务；Claude 子代理不计顶层名额，但仍会使用执行模型的用量。Orca 当前没有接入这套统一配额。[托管实现](../plugins/claude-code/scripts/lib/managed-service.mjs)

## 4. 执行期间保持模型配置稳定

先确认 Claude 能单独工作，再指定模型。可以说“实现使用当前配置的〈模型〉，审查继承当前配置”。模型名称或槽位必须存在，插件不会替你改 CCswitch。

不要在一项正在执行的工作中随意切换供应商配置。如果确实需要切换，先停下当前工作并交接，再确认续接所用配置。成本需要同时观察 Codex 与执行模型的实际用量；子代理和重复返工也会消耗用量。

## 5. 追加约束时继续原任务

对 Codex 说“给〈任务名称〉追加这个要求”，避免重新派发一个相同目标。普通托管有持久队列和稳定请求 ID；回执不明时先核对状态，不用新请求重复发送。

Orca 当前上一条指令未确认完成时不会继续追加；等完成后再发下一条。终端接收输入、Claude 记录指令与完成结果是不同阶段，不能把“接收了”当成“做完了”。[Orca 实现](../plugins/claude-code/scripts/lib/Orca会话.mjs)

## 6. 人类与 Codex 交替操作同一会话

普通托管窗口中你可以亲自输入，之后用 `/交还` 交回控制。Codex 默认等当前轮与已排队的人类指令完成；明确要求“立即接管”才中断。

Orca 接入前确认当前轮、人类队列与草稿已处理，提供准确的目录和 Claude UUID。接入后你可以继续操作，Codex 保留绑定与观察；等人类指令完成后理解新增意图并接续。只有明确要求不再使用该会话才释放接入。不要把关闭终端当成交还控制权。

## 7. 验收看证据

让 Codex 核对：目标是否完成、改动范围是否合理、关键逻辑是否正确、你要求的定向检查是否通过。审查报告是输入，最终判断仍由 Codex 完成。

可以这样要求：

> 核对实际差异、独立审查报告和这次任务的验收条件。按我指定的范围运行检查，向我解释通过依据和剩余问题，然后再决定是否合并。

普通托管最多给 Claude 两轮明确修复反馈；仍不通过则由 Codex 接手或说明阻塞。合并冲突能按已定目标判断时由 Codex 解决，业务意图不明时交给你决定。[协作流程](../plugins/claude-code/scripts/lib/managed-workflow.mjs)

## 8. 按交付边界续接

在派发前说“开启后台事件续接，Claude 完成后继续安排审查”。主控配置 `delegate_wake`，关键事件触发 CLI 后续轮；普通进度保存在本地，不为每条输出启动模型。

普通托管与 Orca 均支持本地事件续接。保存当前阶段与领取位置后结束当前 Codex 轮次，后台按空闲状态继续。需要你决定或回执不明时调度会暂停；回来后先看状态。原桌面打开窗口的即时刷新尚未完成验收。[事件续接](../plugins/claude-code/scripts/lib/事件续接.mjs)

默认中频；明确需求可用低频，复杂排查用高频。低频仍保留规划、关键判断、独立审查和最终验收。不要按分钟把任务切成很多轮，也不要为普通进展读取全部历史。[档位与用量](./协作档位与用量.md)

## 9. 让反馈保持短而具体

优先一次读取统一短摘要，按会话与目录区分进度；无变化结束本轮。用户主动要求实时细节时再强制读取。插件不能即时降低正在生成的桌面轮等级，也不能保证主控完全不做多余推理。

平时让 Codex 读取关键事件和新增正文；出现问题再读取相关上下文。反馈写成“这个验收条件未满足，证据是……，请只修这部分”，比重复整份需求更容易继续工作。

短交付写明阶段、结果、实际检查、未解决问题和快照。普通托管需要时传 `process_docs=true`；Orca 派发默认准备 `.协作记录/<任务标识>/`。这些文件默认 Git 忽略，供续接使用。需要追溯时按原目录与精确 UUID 分页读取历史，屏幕游标和正文游标分别使用。

主轮结束不代表后台工具或子代理结束；取消回执不明时暂停派发。准备验收前核对稳定快照，改动发生后重新审查。
