# 验收与续接

## 原生工作流

用稳定 request_id 创建或推进 `delegate_workflow`，保存 workflow_id、item_id、事件与正文领取位置。完成实现后以稳定快照审查，最多两轮 revise；仍不通过进入 Codex 接手。accept 须实际检查结论和短交付摘要；业务冲突的取舍由用户决定。

用户说继续时 list/status 定位同一工作，恢复阶段与领取位置。已接收的指令不重发；pendingOperations 先核对。独立实现、审查和合并工具仍需各自的真实前置条件，不因文档声称 ready 就跳过。

## Orca

attach 原目录、精确 session_id、idle_confirmed；create 在已注册工作区新建。返回的 id 用于 send/status/transcript/release/takeover/cancel。send 使用稳定请求 ID，上一条未确认完成不重复派发。

Orca 支持事件续接与分档，但没有自动合并和统一执行预算。Codex 可核对其实际改动与用户验收条件；独立工作树、审查方式或最终合并安排须按实际项目选择，不调用 native 工具操作 Orca id。

## 后台协调

权限和求助绕过普通静默期，但主控忙碌时保留队列。审批记录区分 awaiting_codex、awaiting_human、decided 和 invalidated；只传 decision_id 可查原记录。转人工表示审批升级，不代表用户接管了代码。

续接失败先用 diagnose 看最新调度故障、观察心跳和通知回执，再用 inspect 查看具体 CLI 分类。暂停时保留事件和本地提醒；系统报告通知显示不代表用户已经阅读。旧 CLI 运行确认不解除新调度故障。用量缺失报告不可获取，不将全零差值当已验证零成本。

调用 delegate_wake(start) 后，本地观察不调用模型，阶段事件经过档位过滤。Codex忙碌时队列保留，空闲才按精确存储会话 ID 续接。普通进度回传仅保存；求助、失败、方向变更及需决定的交付优先。start不解除故障，workerReady也不是业务链路验收。

唤醒包包含逐份报告及 readyForReview，足够时不重复查询。结果按事件填写 results：event_id、outcome（processed/deferred）、summary。未处理项继续保留并暂停核对，不自动重试相同模型轮；手工处理后用pickup精确领取，再核对当前run决定resolve。稳定性证明不是业务验收；历史报告不得用当前代码快照冒充旧版成果。

轻量 context_sync 轮使用真实 low 配置；深度轮恢复首次捕获或用户显式指定的 deep_effort。CLI不支持等级或实际记录无法确认时如实报告，不把提示词当运行参数。当前正在生成的桌面轮次不能被插件即时降档。

每个后台轮读取短状态／交付，做当前决策，派发后保存 checkpoint 并退出。不要在一个自动轮中持续 wait、sleep 或重复读屏。状态不明／needs_user 会暂停，用户回来以精确 run_id 核对后 resolve；disable 停调度，不取消执行任务。

当前打开桌面窗口的即时刷新仍需独立验证。后台存储续接成功不等于图形界面已经同步。
