# 任务与交付

## 任务模板

```text
任务：一句话说明可观察结果
范围：允许修改的模块；必须保持的行为
验收：具体结果和必要检查
交付：回传结果摘要、改动版本、实际检查与遗留问题
```

规划一次，不把实现定位再次完整做一遍。可以让 Claude 自主定位与修复常见错误；范围、模型或业务方向变更交给 Codex。不要每个工具调用都提交阶段交付。

正文面向执行者和人类读者。不要写“我作为主控已经读取/判断/接管”等操作过程；首次交接补充必要背景，返工只给差异。目录、模型和请求编号优先使用工具字段。必要业务约束、失败证据和版本不可为缩短正文而省略。

有本轮主动回传入口时优先使用：MCP 的 report 或派工附带的 CLI 命令。相同 report_key 只用于重试相同内容，修订交付使用新编号。报告完成后等待主控验收，不反复查询收据。未加载 MCP 的既有会话使用 CLI，不要求为回传重启正在执行的会话。

## 过程目录

`delegate_coordination(prepare)` 返回 `.协作记录/<任务ID>/` 和三个文件位置。默认排除 Git。任务说明记录约定，当前交付仅保留最新短交付，验证记录保存必要证据；不要写凭据或私密原始日志。

当前交付.md 包含 JSON 代码块：

```json
{
  "task_id": "工具返回的执行记录ID",
  "phase_id": "本任务内唯一的阶段编号",
  "level": "milestone",
  "requires_decision": false,
  "summary": "完成项与改动范围，最多1500字",
  "checks": ["实际执行的检查与结果"],
  "unresolved": [],
  "snapshot": "capture"
}
```

level 可为 subtask、milestone、batch、review、final。`requires_decision=true` 表示必须由主控决定才能继续，三档都及时处理；不要把所有普通进展标成 true。

snapshot=capture 由观察器核验真实工作目录；需要审查的交付须完成当前轮并在两次观察中保持稳定。文件变化后旧快照失效，不能用旧报告验收新代码。检查未执行、跳过或失败时如实记录。

## 返工模板

```text
未满足：具体验收条件
证据：首次真实失败、必要文件／行号、失败前置条件
修复范围：仅本次问题
再验收：需要重复的相关检查
```

先查错误与前置，不先猜端口或配置。一次集中反馈；红绿回放和临时切换旧代码期间不做最终审查。

## 执行中的补充与后台服务

新增反例、限制或检查证据使用delegate_coordination的evidence，绑定当前task_id、backend、request_id和唯一evidence_id；新业务仍走任务队列。用evidence_status核对saved/read/acknowledged，不因saved便报告Claude已采用。执行端在阶段边界读取inbox，不靠频繁催问推进。

确认后台项是下一阶段需要的开发服务时，使用background_role标记service并说明依据；不要把未完成审查冒充服务。服务保留记录会阻止资源清理。确已停止或交接后，按原request_id、background_id及依据设released，不自动杀共享服务。
